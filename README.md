# fprime-cpp-codegen

A Python package for generating C++ code for F Prime.

It builds C++ documents — one `.hpp` plus one or more `.cpp` files — through a
Builder-pattern API, where nesting in the generated C++ follows nesting in the
Python. It generates general-purpose C++: classes, structs, templates, namespaces,
enums, free functions, statements. Nothing in it knows about the FPP model, and it
has no runtime dependencies.

## Installation

```sh
pip install git+https://github.com/fprime-community/fprime-cpp-codegen.git
```

Requires Python 3.10 or newer.

## Quick start

```python
from fprime_cpp_codegen import CppDocBuilder, Output

doc = CppDocBuilder("Ring", description="a fixed-capacity ring buffer",
                    namespaces=["Demo"], tool_name="ring-buffer-example")
doc.include("Fw/FPrimeBasicTypes.hpp")
doc.include("Ring.hpp", output=Output.CPP)

with doc.namespace("Demo") as ns:
    with ns.class_("Ring", comment="A ring buffer of fixed capacity") as cls:
        with cls.public("Types"):
            status = cls.enum_class("Status", underlying="U8",
                                    comment="The result of an operation")
            status.constant("OK", 0, comment="The item was stored")
            status.constant("FULL", 1, comment="The buffer is at capacity")

        with cls.public("Constructors and destructors"):
            ctor = cls.constructor(explicit=True, comment="Construct an empty ring")
            ctor.param("U32", "capacity", comment="The capacity, at most CAPACITY")
            ctor.init("m_head(0)", "m_size(0)", "m_capacity(capacity)")

        with cls.public("Public member functions"):
            push = cls.function("push", ret=status.type, comment="Append one item")
            push.param("U32", "item", comment="The item to append")
            with push.body as b:
                with b.if_("m_size == m_capacity"):
                    b.ret("Status::FULL")
                b.assign("m_data[(m_head + m_size) % CAPACITY]", "item")
                b.line("m_size++;")
                b.ret("Status::OK")

            cls.function("size", ret="U32", const=True, inline=True,
                         body="return m_size;",
                         comment="The number of items currently stored")

        with cls.private("Member variables"):
            cls.var("U32", "CAPACITY", init="64", static=True, constexpr=True,
                    comment="The largest capacity a ring can have")
            cls.var("U32", "m_data", array="CAPACITY", comment="The stored items")
            cls.var("U32", "m_head", comment="Index of the oldest item")
            cls.var("U32", "m_size", comment="How many items are stored")
            cls.var("U32", "m_capacity", const=True, comment="The chosen capacity")

doc.write("build-artifacts")
```

That yields `Ring.hpp`:

```cpp
// ======================================================================
// \title  Ring.hpp
// \author Generated by ring-buffer-example
// \brief  hpp file for a fixed-capacity ring buffer
// ======================================================================

#ifndef Demo_Ring_HPP
#define Demo_Ring_HPP

#include "Fw/FPrimeBasicTypes.hpp"

namespace Demo {

  //! A ring buffer of fixed capacity
  class Ring {

    public:

      // ----------------------------------------------------------------------
      // Types
      // ----------------------------------------------------------------------

      //! The result of an operation
      enum class Status : U8 {
        OK = 0, //!< The item was stored
        FULL = 1, //!< The buffer is at capacity
      };

    public:

      // ----------------------------------------------------------------------
      // Constructors and destructors
      // ----------------------------------------------------------------------

      //! Construct an empty ring
      explicit Ring(
          U32 capacity //!< The capacity, at most CAPACITY
      );

    public:

      // ----------------------------------------------------------------------
      // Public member functions
      // ----------------------------------------------------------------------

      //! Append one item
      Status push(
          U32 item //!< The item to append
      );

      //! The number of items currently stored
      inline U32 size() const
      {
        return m_size;
      }

    private:

      // ----------------------------------------------------------------------
      // Member variables
      // ----------------------------------------------------------------------

      //! The largest capacity a ring can have
      static constexpr U32 CAPACITY = 64;

      //! The stored items
      U32 m_data[CAPACITY];

      //! Index of the oldest item
      U32 m_head;

      //! How many items are stored
      U32 m_size;

      //! The chosen capacity
      const U32 m_capacity;

  };

}

#endif
```

and `Ring.cpp`:

```cpp
// ======================================================================
// \title  Ring.cpp
// \author Generated by ring-buffer-example
// \brief  cpp file for a fixed-capacity ring buffer
// ======================================================================

#include "Ring.hpp"

namespace Demo {

  // ----------------------------------------------------------------------
  // Constructors and destructors
  // ----------------------------------------------------------------------

  Ring ::
    Ring(U32 capacity) :
      m_head(0),
      m_size(0),
      m_capacity(capacity)
  {

  }

  // ----------------------------------------------------------------------
  // Public member functions
  // ----------------------------------------------------------------------

  Ring::Status Ring ::
    push(U32 item)
  {
    if (m_size == m_capacity) {
      return Status::FULL;
    }
    m_data[(m_head + m_size) % CAPACITY] = item;
    m_size++;
    return Status::OK;
  }

}
```

The complete script is in [`examples/ring_buffer.py`](examples/ring_buffer.py).

A few things happened there without being asked for. The `inline` accessor was
defined in the header, because an `inline` function defined in a single `.cpp`
would not link from anywhere else. `Status` came out as `Ring::Status` in the
source file but bare `Status` in the header, because a return type precedes
`Ring::` and so is not yet inside the class's scope. The `Types` and
`Member variables` banners stayed out of the source file, since neither section
has anything to say there.

## `with` is optional

A builder attaches to its parent the moment you create it, so its position in the
output is already fixed and you can keep filling it in afterwards:

```python
fn = cls.function("bump", ret="U32")
fn.param("U32", "by", default="1")
fn.body.ret("m_count += by")
```

Use `with` where you want the visual grouping. Two places it earns more than that:

- **Access sections.** A section that ends up with no members removes its own
  `public:` label and banner, so a conditionally generated group leaves no trace
  when it generates nothing.
- **Preprocessor guards.** `with cls.if_directive("#ifdef BUILD_UT"):` emits
  nothing at all if no members were added inside it.

Both discard what they added if an exception passes through them.

## Generating from a data model

Most real generators map over a model rather than writing classes out by hand.
Builders are values, so a helper can take a scope and add to it, or build a
fragment and hand it back:

```python
def accessor(cls, field):
    fn = cls.function(f"get{field.name}", ret=field.type, const=True,
                      comment=f"Get {field.name}")
    fn.body.ret(f"m_{field.name}")

with cls.public("Accessors"):
    for field in model.fields:
        accessor(cls, field)
```

`Body` works the same way — build one anywhere and splice it in:

```python
def null_check(name: str) -> Body:
    frag = Body()
    with frag.if_(f"{name} == nullptr"):
        frag.ret("Status::INVALID")
    return frag

with fn.body as b:
    for arg in ("src", "dest"):
        b.extend(null_check(arg))
```

## One header, several source files

Every definition can name the `.cpp` file it belongs to. The header always
declares everything; a source file only gets what names it. That is how one large
generated class gets split across translation units without duplicating its
declaration.

```python
with doc.cpp_file("RingHelpers"):
    cls.function("rebalance", body="...")   # lands in RingHelpers.cpp
```

Or per definition: `cls.function("rebalance", cpp_file="RingHelpers", ...)`.

Rendering discovers the supplemental files itself, so nothing is silently dropped
for want of naming it:

```python
doc.files()          # {"Ring.hpp": ..., "Ring.cpp": ..., "RingHelpers.cpp": ...}
doc.write("out")     # writes all three
```

`write()` leaves a file alone when its contents already match, so a no-op
regeneration does not cascade a rebuild through everything downstream. The
`WriteResult` it returns says which files were written and which were not.

Decoration follows the members it decorates. A section banner goes to the default
source file when that file has any of the section, and relocates to the
supplemental file when it does not, so it never heads an empty stretch. A
preprocessor guard is repeated into *every* source file holding one of its
definitions — a guard is not decoration, and a definition that escaped it would be
compiled unconditionally.

## Where a definition goes

Most definitions go to a source file. These go in the header instead, because C++
requires them to be visible in every translation unit that uses them:

| Kind | Why |
| --- | --- |
| `template=...` | A template's definition must be visible at every use |
| any member of a templated class | Inherits that requirement |
| `inline=True` | Would not link from another translation unit |
| `constexpr=True` | Same |
| `inline_body=True` | You asked for it |

And these have no definition to place at all: `deleted=True`, `defaulted=True`, and
a `pure_virtual=True` function with no body. A pure virtual *with* a body does get
one — that is a default implementation, which C++ permits.

## Statements

`Body` covers the ordinary control flow. Scopes are context managers:

```python
with fn.body as b:
    b.var("U32", "total", "0")
    with b.for_("U32 i = 0", "i < n", "i++"):
        with b.if_("m_data[i] == 0"):
            b.continue_()
        b.line("total += m_data[i];")
    with b.switch("kind") as sw:
        with sw.case("Kind::A", "Kind::B"):
            b.call("handle", "kind")
        with sw.default():
            b.raw(fprime.write_assert("0"))
    b.ret("total")
```

`if_` / `elif_` / `else_` chain, and `elif_`/`else_` raise `ScopeError` if there is
no `if` immediately before them to attach to — including when a statement has come
between, which would otherwise re-point the `else` at the wrong `if`. For a chain
whose length comes from the model, `branch()` opens an `if` the first time and an
`else if` while the chain is still open:

```python
for condition, code in dispatch:
    with b.branch(condition):
        b.add(code)
with b.else_():
    b.raw(fprime.write_assert("0"))
```

`case` bodies get braces and an automatic `break;` — unless the arm already ends in
a `return`, `break`, `continue` or `throw` at that level, in which case the `break;`
would be unreachable. That is tracked state, not a guess at the text: a `return`
nested inside an `if` still gets its `break;`, because the `if` may not be taken.
Pass `fallthrough=True` to suppress it outright.

Body scopes emit even when they turn out empty, because a vanishing `if` would
silently change what a following `else` attaches to. Pass `omit_if_empty=True`
where you would rather the scope disappear.

`add()` takes anything statement-shaped — text, a `Line`, another `Body`, or nested
sequences of those — and skips `None`, so a conditional fragment needs no branch at
the call site:

```python
b.add(preamble, check if channel.limit else None, "return Status::OK;")
```

## Examples

| Script | What it covers |
| --- | --- |
| [`ring_buffer.py`](examples/ring_buffer.py) | A hand-written class. Start here. |
| [`fpp_constants.py`](examples/fpp_constants.py) | A document with no class in it: constants at namespace scope, split across the two files by `extern`. |
| [`fpp_enum.py`](examples/fpp_enum.py) | A port of FPP's enum autocoder — the biggest thing here, and the closest to a real generator. |

The two `fpp_*` scripts are ports of [`fpp-to-cpp`](https://github.com/nasa/fpp)'s
own autocoders, driven by a small Python data class in place of the FPP model. They
are checked against unmodified reference output from `fpp`'s test suite, kept in
`tests/goldens/fpp/`:

- `fpp_constants.py` reproduces **both** files byte for byte.
- `fpp_enum.py` reproduces the 148-line `.cpp` byte for byte, and the 222-line
  `.hpp` except for two lines where upstream indents a `#ifdef` block inside an
  inline constructor to four spaces while the statements around it sit at six. This
  package keeps the body consistent. The test asserts the difference is *exactly*
  those two lines and *only* indentation, so any real drift fails.

Both are compiled as part of the test suite, the enum twice — once plainly and once
with `-DBUILD_UT -DFW_SERIALIZABLE_TO_STRING=1`, since otherwise most of the
generated code sits inside a `#if` and never reaches the compiler.

Run one to see its output:

```sh
python examples/fpp_enum.py              # print both files
python examples/fpp_enum.py build-dir    # write them out
```

## The layers

The builder is the recommended entry point, not the only one. Everything under it
is public, and you can drop down a layer wherever it suits you.

| Module | What it is |
| --- | --- |
| `builder` | `CppDocBuilder` and friends — the builder API |
| `body` | `Body`, `Switch` — function bodies from statements |
| `doc` | The document IR: frozen dataclasses you can build by hand |
| `writer` | `HppWriter` / `CppWriter` — visitors rendering the IR to lines |
| `utils` | Helpers over `list[Line]`: `wrap_in_*`, calls, sums, enum constants |
| `comments` | Doxygen comments, banners, access tags |
| `lines` | `Line` and the line algebra everything is built on |
| `output` | Rendering to text and to disk |
| `errors` | `CppCodegenError`, `ScopeError`, `ValidationError` |
| `fprime` | F Prime conventions — import it explicitly |

The layers compose. `utils` and `fprime` return `list[Line]` and lists of IR
members, and the builder takes both:

```python
cls.member(*fprime.write_ostream_operator("MyType", body))          # IR members
fn.body.raw(utils.write_function_call("log_FOO", ["id"], fields))   # lines
fn.body.raw(fprime.write_assert("id < COUNT", "id"))                # lines
```

Note that `cls.function(...)` both creates the function *and* attaches it, so do
not also pass its `build()` to one of the list-style guard helpers — that would add
it twice. To guard members you are creating through the builder, guard them in
place:

```python
with cls.if_directive(fprime.FW_ENABLE_TEXT_LOGGING):
    cls.function("describe", const=True, body="...")
```

The `fprime.guard_*` helpers are for members you already hold as IR.

A `Line` carries its indentation separately from its text. That is what lets a
doxygen post-comment hang under an arbitrary column of the line above it, and what
makes a blank line render genuinely empty rather than as trailing whitespace.

## The F Prime layer

`fprime_cpp_codegen.fprime` holds the conventions that show up in every autocoded
F Prime file: the standard header lists, `FW_ASSERT`, the
`Fw::ExternalString`-over-a-buffer idiom, `FW_ENABLE_TEXT_LOGGING` and `BUILD_UT`
guards, and the unit-test `operator<<`. It is all still strings and lines — it does
not know about the FPP model any more than the rest of the package does. Import it
explicitly; the core API stays framework-neutral.

## Relationship to `fpp` and `fprime-python-model`

The design is modelled on the `CppDoc` writers in
[`fpp`](https://github.com/nasa/fpp) and their Python translation in
[`fprime-python-model`](https://github.com/fprime-community/fprime-python-model),
and the formatting matches theirs, so generated code reads the same alongside
existing F Prime autocode. `tests/goldens/` holds three files copied byte-for-byte
from `fpp`'s own `CppWriter` test output; the test suite reproduces all three
through both the IR and the builder. That is a check against formatting drift, not
a compatibility contract.

The API itself departs where the original was awkward:

| `fpp` / `fprime-python-model` | Here |
| --- | --- |
| Nested case-class literals with positional `None`s | Builders with keyword arguments |
| Nine `Member`/`ClassMember` wrapper types | Union types, dispatched by `isinstance` |
| `guardedList` conditionals | Ordinary Python `if` |
| `Option[String]` cpp-file names threaded through every call | A `with doc.cpp_file(...)` block |
| `SVQualifier` etc. as two-valued enums | Booleans, validated against each other |
| No templates, `noexcept`, `= delete`, `= default`, `constexpr`, `inline`, variables | All supported |
| Callers must list supplemental `.cpp` files | Discovered automatically |
| `stripMargin` mistranslated, corrupting `a \| b` | Correct margin semantics |
